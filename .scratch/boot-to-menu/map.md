## Destination

Boot the recompiled X-Men Legends port to the main menu — CLAUDE.md's own
"definition of done." This is goal 1 of a larger effort (the user has said
more goals follow once this map is charted); re-scope this map or start a
new one when goal 1 closes rather than silently expanding it.

## Notes

- Domain: static PC recompilation of an Xbox XBE (X-Men Legends). Working
  tree is `src/game/` inside this repo.
- Skills every session on this map should consult: the recomp MCP tools
  (`mcp__OddityRecomp__*` — probe, deepdive, faithful, walls_report, ledger,
  progress) over raw shell wherever they cover the job. `mcp__ReVa__*` for
  Ghidra-side disassembly/decompilation questions.
- For any `grilling`-type ticket that is really "diagnose this wall" (a spin,
  a crash, an esp escape), consult `.claude/skills/diagnosing-bugs/SKILL.md`
  alongside the MCP tools — its Phase 3 (3-5 ranked, falsifiable hypotheses
  before touching a probe) and Phase 4 (one probe per hypothesis, not
  log-everything) formalise the discipline rules #5-#9 already require, and
  its Phase 1 feedback-loop framing maps directly onto walls.py + progress.py.
- Standing rules from this repo's CLAUDE.md (`## The 15 rules`) apply to any
  ticket that touches code — notably #5 (probe, don't guess), #7 (one
  behaviour change per build), #8 (a fix needs a second signal), #9 (a bug
  seen twice is a class).
- Ledger (`mcp__OddityRecomp__ledger`) already holds refuted/confirmed claims
  from prior sessions — check it before opening a research thread that may
  already be dead.
- Budget awareness: recent agent fan-out burned ~60% of the session limit in
  one go. Prefer direct MCP tool use over spawning agents on this map unless
  a ticket genuinely needs parallel/background work.
- **The engine is Vicarious Visions Alchemy** — confirmed 2026-08-08 from
  the game data itself, not inferred: `src/game/game/alchemy.ini` is headed
  "Alchemy.ini for X-Box", and the XBE references `alchemy.ini`,
  `showLeaksOnExit` and `defaultReportLevel`. It is licensed middleware, not
  a Raven in-house engine, which matters twice over: the engine layer —
  where every wall so far has lived — is shared code rather than
  title-specific, and X-Men Legends II (2005) shipped a **Windows x86**
  build on that same engine while XML1 never did. Xbox is x86 too, so the
  two binaries are directly comparable at the instruction level. That is the
  premise behind tickets 11 and 12.
- **The allocator under investigation is Alchemy's memory manager**, not
  game-specific code and not the CRT. Its shape always said so — manager
  object, pools, free lists, coalescer, a configurable leak tracker — and
  the engine confirmation settles it. Consequence: every allocator wall so
  far has been in *middleware that shipped working on PC in XML2*, which is
  the strongest argument for ticket 12.
- **The engine embeds Python for game logic.** The XBE carries
  `PythonGameInterface`, `BEHAVED`, `py_Safe`, `py_counter`; XML2's asset
  tree contains ~1,700 `.py` entity scripts headed "Generated by BehavEd"
  (Raven's own behaviour editor). Booting to a *menu* may not need the
  interpreter, but anything past that will — relevant to goal 2, not goal 1.
- **The XBE carries 562 MSVC RTTI class names and the project has never
  used them** (found 2026-08-08). Ghidra's program has 41 non-default
  symbols; every one of the 26,506 functions is `sub_XXXXXXXX`. The named
  classes include `IAlchemyObjectPool`, `CMemory`, `IMemoryPoolInfo@CMemory`
  and `IChuckAllocator` — precisely the allocator we have been reversing
  blind. No RTTI analyzer applies to an XBE, so this needs a script, not a
  setting → ticket 13, which outranks 11/12 because it needs no second
  binary.
- **The boot has still never touched a file.** Zero
  `NtCreateFile`/`NtReadFile`/`NtOpenFile` in the current log, so the game
  dies before it reads `alchemy.ini` or loads any asset. Two consequences:
  the `alchemy.ini` settings cannot be influencing the current wall, and no
  amount of asset/data-format knowledge helps goal 1.

### Roadmap beyond goal 1 (future maps, not this one's scope)

Full project destination, per the user (2026-08-08): a fully decompiled and
statically recompiled PC port with full rendering, GPU upscaling, modernized
graphical settings, Blender-remastered assets, and lossless/upscaled
cutscenes. This map (boot-to-menu) is goal 1 only — do not silently absorb
any of the below into it; each becomes its own wayfinder map once charted.

Grounded against what this repo and its upstream (`sp00nz/xboxrecomp`)
actually have — checked 2026-08-08, see `docs/technical/gap-analysis.md`,
`src/d3d/README.md`, `src/nv2a/README.md` for the source of these claims:

**Already built (do not re-decide these)**
- Rendering backend: D3D8→D3D11 translation is the committed architecture
  (`src/d3d/`), not an open choice. NV2A GPU emulation extracted from xemu
  (`src/nv2a/`) — register combiners, vertex shader microcode, 8-light T&L,
  vertex fog all marked DONE in the gap analysis.
- Audio: XAudio2 backend (`src/apu/apu_xaudio2.c`) + DirectSound wrapper +
  64-voice APU processor, DONE.
- Input: XInput backend, 4 controller ports, rumble, DONE.
- Kernel (memory, threading, sync, crypto, file I/O): DONE.

**Goal 2 candidate — full playable completeness**
- Every level, save/load, no crashes end-to-end — not just the menu.
- Gap analysis flags real per-title unknowns worth a research ticket once
  rendering starts producing frames: which of the PARTIAL/MISSING items
  (17/66 texture formats covered, mipmaps level-0-only, no cube/volume
  textures, no WMA audio decode, no per-pixel/table fog, no 3D positional
  audio) X-Men Legends actually exercises. The gap analysis was written
  against Blood Wake/Wreckless, not this game — don't assume its priorities
  transfer without checking.
- **Local split-screen co-op.** X-Men Legends is built around on-console
  split-screen co-op. Nothing in `docs/technical/` addresses multi-viewport
  rendering, and `src/d3d/` reads as a single-device/single-viewport design
  (`d3d8_device.c`'s README walkthrough shows one device, one present).
  Whether split-screen is architecturally supported or needs real new work
  is unresolved — check before assuming it's a settings toggle away.
- **Save format migration.** Xbox save → PC save conversion isn't addressed
  anywhere in the current docs; needed for "full playable completeness" to
  mean anything past a single session.
- **Multi-dump / multi-revision testing.** `tools/setup_game` verifies the
  disc against a manifest of known-good dumps; worth a QA goal around
  region/revision coverage (PAL/NTSC, disc revisions) rather than only the
  one dump development has used so far.

**Goal 3 candidate — modernization layer (genuinely new, nothing upstream covers this)**
- GPU upscaling: FSR/DLSS/XeSS integration on top of the D3D11 backend.
- Modern settings menu: uncapped framerate, widescreen/ultrawide unlock
  (game is native 4:3), AA, anisotropic filtering, shadow quality, FOV
  slider, HDR, V-sync.
- Accessibility: subtitles, colorblind modes, difficulty options.
- **Fixed-timestep desync risk.** Unlocking framerate is a known port
  landmine — game logic/animation/AI is likely tied to the original 30fps
  tick. Needs its own ticket to decouple sim-rate from render-rate; don't
  fold this into "add an FPS slider" and assume it's cosmetic.
- **HUD/UI reflow, not just a wider viewport.** Menus and HUD were laid out
  for 4:3/480p. Widescreen unlock without reflow just stretches or
  letterboxes 4:3 UI on a 16:9+ canvas — a distinct piece of work from the
  render-surface change itself.

**Goal 4 candidate — asset remaster**
- Texture pipeline: extract originals, AI-upscale or hand-redo.
- Blender pipeline: import original models, re-topo/re-texture to PBR for a
  genuine redo rather than filtered textures.
- Cutscene pipeline: then decide real-time re-render vs. lossless AI video
  upscale.
- **The format problem is largely already solved by the modding community**
  (found 2026-08-08 via `github.com/EthanReed517/XML2-Ultimate-Patch`, an
  XML2 overhaul project, and the MarvelMods forum behind it). That tree
  carries ~18,900 `.igb` files (Alchemy's Intermediate Graphics Binary model
  format), ~2,300 `.xml` / 33 `.xmlb` (Alchemy binary XML), 543 `.zam` and
  other audio, and — most valuable for a Blender pipeline — **736 `.max`
  3ds Max source files**. A community that ships an overhaul patch has
  working import/export for these formats, so goal 4 should start by
  surveying existing tooling rather than writing IGB parsers from scratch.
  Same engine as XML1, so the formats should carry over — verify rather than
  assume, since XML2 is a year newer.
- **Cutscene codec is probably `.sfd`** — 63 such files in that tree, which
  is conventionally Sofdec (CRI Middleware) MPEG. That would answer goal 4's
  "codec unknown" research question, but treat it as a strong lead needing
  confirmation against XML1's own media, not as established fact.
- **The "ship no game data" rule applies here too, and it's easy to miss.**
  CLAUDE.md's rule isn't just about the base port — an AI-upscaled texture,
  a re-topologized model, or an upscaled cutscene video are all derivative
  works of copyrighted Marvel/Activision assets, same as the originals.
  The pipeline/tooling that *generates* these from the user's own disc dump
  ships; the generated outputs (textures, models, video files) do not,
  exactly like `src/game/src/recomp/gen/` is gitignored today. This isn't a
  new open question so much as an existing constraint that's easy to forget
  once "asset remaster" sounds like a content project rather than a tooling
  one — worth stating explicitly before goal 4 is charted, not discovered
  after someone commits a remastered texture pack.
- **Live original/remastered toggle (Tomb Raider I-III Remastered style)**,
  raised 2026-08-08 — deliberately not decided yet, revisit when this map is
  actually charted. The user is interested in exploring *both* of two
  different-shaped efforts, not picking one now:
  - A drop-in-replacement pipeline (preserves original skeleton/bone weights
    and collision so a runtime toggle can swap the asset set without
    touching gameplay) — this is what a live in-game toggle actually
    requires.
  - A free redo (no constraint to match original topology/rigging) — better
    art results, but forecloses the live-toggle option; would ship as a
    replace-outright remaster instead.
  These aren't compatible within one asset set — the constraint that makes
  the toggle possible is the same constraint that limits how far the art can
  depart from the original. Worth prototyping a small test case of each
  (one model, one texture) before committing goal 4's whole pipeline to
  either shape.

**Goal 5 candidate — platform polish**
- Native KB/M support, rebindable controls (XInput backend exists but game
  is currently gamepad-only at the input-mapping level).
- Steam integration (achievements, rich presence) — optional.
- Modding: the asset/level format work goal 4 needs doubles as a modding
  toolchain if exposed deliberately.
- **Installer/launcher UX.** Expand past the current dev-facing
  `tools/setup_game` script into a guided disc-verify-and-build flow for
  end users who aren't building from source.
- **Advanced controller haptics** (DualSense adaptive triggers, Steam Deck
  HD haptics) beyond the basic binary rumble XInput already provides.

**Goal 6 candidate — SteamOS / Steam Deck / Steam Machine support**
**Scope decided 2026-08-08: hardware/OS support only, no Steam store
listing.** Launched as a non-Steam Windows exe (via Proton) or a standalone
Linux build in desktop mode — same posture as UnleashedRecomp/OpenGOAL, and
consistent with this repo's existing "bring your own disc, ship no game
data" model. A store listing would raise real IP questions (X-Men Legends is
Marvel/Activision-owned) that BYO-disc distribution sidesteps; that
distinction is *why* the model exists, so don't drift toward a store listing
without re-opening this decision explicitly.

Checked upstream state 2026-08-08: this is NOT starting from zero, but it's
also not one thing — two genuinely different paths exist and picking between
them is itself the first ticket whenever this map is charted:
- **Path A — Proton.** Run the existing Windows D3D11 build under Proton on
  SteamOS. Likely the cheapest route to "works on Deck" — mostly
  verification (does DXVK translate the D3D11 calls cleanly, does
  performance hold on the Deck's APU) rather than new backend work.
- **Path B — native Linux.** `src/d3d/d3d8_gl.c` is an SDL2 + OpenGL 3.3
  backend already started upstream, explicitly marked "first cut" — real
  Clear/Present/BeginScene/DrawPrimitive(UP) work, but VSH bytecode→GLSL and
  register-combiner→GLSL translation are still TODO (the D3D11 path already
  solved the equivalent HLSL generation in `d3d8_vsh.c`/`d3d8_combiners.c`,
  so this is porting known logic to a new shader language, not inventing it
  from scratch). `tools/linux/install_deps.sh` already exists.
- Steam Deck specifics either path needs: verified-badge checklist (UI
  legible at 1280x800, controller-only navigation, on-screen keyboard for
  any text entry), Steam Input glyph mapping on top of the existing XInput
  backend, cloud save compatibility, suspend/resume handling.
- Don't assume Path B is required — Path A may clear the bar for "Steam Deck
  support" on its own and is far cheaper. Charting session should settle
  this before ticketing anything else on that map.

**Goal 7 candidate — performance optimization**
Cross-cutting rather than a clean dependency of any one goal above — but
matters most once goal 6 (Deck's constrained APU/TDP) and goal 3 (upscaling
adds GPU cost) are both in play, so sequence it alongside/after those two
rather than before:
- Kernel threading is currently a "single-thread cooperative model" (per
  `gap-analysis.md`) — profile whether this is a real bottleneck before
  assuming multi-core work is needed; don't optimize the unmeasured.
- Shader cache precompilation/warm-start (both `d3d8_vsh.c`'s 64-entry cache
  and `d3d8_combiners.c`'s 128-entry cache currently compile on first use —
  worth checking if that causes traversal stutter) rather than only at
  runtime.
- Texture streaming / memory footprint, relevant for Deck's shared 16GB pool
  specifically.
- Frame pacing / VRR — matters more on Deck (fixed power budget) than desktop.
- **Load-time / level-streaming.** Original pacing assumes Xbox DVD/HDD
  speeds. On modern SSDs there's room to background-stream and cut load
  screens substantially — worth its own ticket rather than assuming it falls
  out of general optimization work.

**Goal 9 candidate — release & support infrastructure**
Nothing here yet — checked, no `.github/workflows` exists at all. This is
the gap between "runs on my machine" and "a thing other people can rely on":
- **CI.** No automated build/test on push. Matters more once goal 6 adds a
  second platform (Windows + Linux) that can silently drift out of sync.
- **End-user crash reporting/telemetry**, opt-in only. Distinct from the
  dev-facing `triage_crash.py` — that's for diagnosing walls during
  development; this is for hearing about problems after something ships.
  Given the project's existing privacy-conscious posture (ship no game data,
  no network stubbed in rather than silently phoning home), default this to
  explicitly opt-in, not opt-out.
- **End-user documentation.** Every doc in `docs/` today is dev-facing
  (pipeline internals, formats, debugging notes). Nothing walks a non-technical
  player through dumping their disc, installing, or troubleshooting a failed
  build — worth its own pass once goal 1 makes there something worth
  documenting for a player rather than a contributor.

**Goal 8 candidate — online co-op**
**Scope decided 2026-08-08: in scope, but a later, non-blocking goal.**
X-Men Legends had Xbox Live co-op on the original console; kernel networking
is currently fully stubbed ("link down" per `docs/formats/kernel-exports.md`
and `docs/pipeline/05-runtime.md`). Full Xbox Live protocol reimplementation
is explicitly not the goal — reimplement co-op over modern netcode (Steam
networking / GameNetworkingSockets or similar) once the single-player game
is solid. Depends on goal 2's local split-screen finding (the co-op
session/rendering model needs to exist locally before it's worth
networking), so sequence this after goal 2, not in parallel with it.

**Sequencing note**: goal 3 (upscaling/settings) sits on top of the D3D11
backend that already exists, so it does *not* block on goal 4 (assets) or
vice versa — they can run as parallel maps once goal 1/2 clear. Goal 4's
cutscene pipeline has an unresolved research dependency (codec identification)
that should be its first ticket whenever that map is charted. Goal 6's
Path A vs Path B choice should happen before goal 7 is charted in detail,
since it decides which backend (D3D11+DXVK vs the OpenGL "first cut") the
optimization work actually targets. Goal 8 (online co-op) waits on goal 2's
split-screen finding.
