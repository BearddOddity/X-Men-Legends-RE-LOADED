Where it stands right now

The list that never grew, because the instruction that appended to it was missing

For months the engine’s type descriptors held field lists that stayed empty, and a dozen crashes downstream all traced back to reading one. The routine that appends an entry ends in a branch the translator never recognised as code, so the store simply never happened — and the same gap dropped sixteen bytes of stack cleanup, which is a leak measured in August and never placed until now. Restoring it moved three of the four tracked signals at once: heap allocations 96 to 136, code reached 170 to 196, call sites 477 to 551, indirect dispatches up 43%. Both reached and call sites are records.

Root cause: one uninitialised object

Inside that initialiser, a type descriptor reaches the create-an-instance path with both its instance size and its allocation prefix set to -1. The code allocates size + prefix, so it asks the heap for 0xFFFFFFFE bytes — roughly 4 GB. The allocator correctly refuses and returns null, and the pointer becomes 0 + (-1) = -1, which passes a non-null check and is written through.

Probing all 235 allocator calls made this unambiguous: the healthy ones request 12, 16, 52 bytes; the fatal one requests 0xFFFFFFFE. Nothing in the chain is misbehaving — not the allocator, not the null check, not the create path. One object was never initialised.

The fix belongs at the top of that chain. Every function below it is faithful to the original and none of them should be guarded. It is also the third time the same defect class — code reachable only through a data pointer, so never translated — has produced the active wall.

The dominant defect class

Code that exists but is never reached

A recompiler discovers functions by following calls from an entry point. A function whose only reference is a pointer in a table — a vtable, an initialiser list, a factory array — is never reached, never translated, and whatever it was meant to set up stays null for the whole run.

The clearest case sits on the most important path in the binary: the CRT startup at 0x001A1C23 is never the target of a call instruction anywhere. Its only reference is push 0x1a1c23, as an argument to CreateThread. It runs at all only because it was hand-written into the port.

The strategic read

Anything that converts data-referenced code into translated code has outsized leverage over fixing individual functions. Two passes of that shape — 609 orphan functions, then 512 data-referenced pointers — have each produced more movement than any single-function fix in this project's history.

What happens next

A wrong idea, killed before it cost a build

The session opened by chasing a hunch: six of fourteen type descriptors appeared to point at another object’s data. Checking the project’s own record of past conclusions refuted it in seconds. The pattern that looked like structure — every healthy descriptor’s list sitting exactly 0x68 bytes past it — is just the allocator handing out consecutive blocks of a 0x64-byte object. The same mistake had been made and withdrawn months earlier. Nothing was aliased.

That is the ledger paying for itself. The wrong idea was appealing, and the only thing that stopped it was having written down why it failed the first time.

What was actually wrong

Measuring instead of guessing found something better. The first lookup worked perfectly — twenty-three entries, match at index thirteen. The second call was the broken one, and bracketing it showed the stack pointer sixteen bytes lower after a call that should have left it untouched, with a saved register coming back holding a neighbour’s value.

Seven measurements down the call chain put the sixteen bytes on one routine: the one that stores an entry into a descriptor’s field list. Its translated form stops early, and the branch it ends on — the branch containing the store itself, plus the register restore and argument cleanup — was never recognised as code. Eight bytes of restore plus eight of cleanup is exactly the sixteen that went missing, and the absent store is why no list ever grew.

This is the third time a two-or-three-instruction fragment the translator skipped has turned out to be the whole defect. It is now the first thing to check when a function’s translated extent is shorter than its real one.

Kernel calls did not move, and that is expected rather than disappointing: the boot now does far more real work before it stops, which the other three counters show and that one cannot. The project’s own rules require a second signal before believing a fix, and here there are three.

The honest caveat

Regenerating any part of the translated tree silently discards the hand-written repairs inside it, duplicates three functions every time, and leaves a link error behind. None of that is detected by the tool that claims to check it. The full repair sequence is now written down, and a new tool fixes the duplication by checking that every label inside a function belongs to that function’s own address range.

An archive of the working tree is taken before and after each of these steps now. Last session one was not, and a file that cannot be rebuilt was lost permanently.
