The high-water mark that was not one

On 9 August a run recorded 4,000 kernel calls and 826 heap allocations against today’s 230 and 136, which reads as a severe regression. It is not. That run was a runaway: 4,000 is where the watchdog cuts execution off, and the change that ended it is recorded as removing a dispatch loop running on junk read from an unmapped page. The allocations were that loop allocating garbage.

Worth stating plainly, because the project’s own progress tool still advertises 4,000 as the best figure ever achieved, and it never was.

Root cause: one uninitialised object

Inside that initialiser, a type descriptor reaches the create-an-instance path with both its instance size and its allocation prefix set to -1. The code allocates size + prefix, so it asks the heap for 0xFFFFFFFE bytes — roughly 4 GB. The allocator correctly refuses and returns null, and the pointer becomes 0 + (-1) = -1, which passes a non-null check and is written through.

Probing all 235 allocator calls made this unambiguous: the healthy ones request 12, 16, 52 bytes; the fatal one requests 0xFFFFFFFE. Nothing in the chain is misbehaving — not the allocator, not the null check, not the create path. One object was never initialised.

And where that object comes from

The fix belongs at the top of that chain. Every function below it is faithful to the original and none of them should be guarded. It is also the third time the same defect class — code reachable only through a data pointer, so never translated — has produced the active wall.

The dominant defect class

Code that exists but is never reached

A recompiler discovers functions by following calls from an entry point. A function whose only reference is a pointer in a table — a vtable, an initialiser list, a factory array — is never reached, never translated, and whatever it was meant to set up stays null for the whole run.

The clearest case sits on the most important path in the binary: the CRT startup at 0x001A1C23 is never the target of a call instruction anywhere. Its only reference is push 0x1a1c23, as an argument to CreateThread. It runs at all only because it was hand-written into the port.

The strategic read

Anything that converts data-referenced code into translated code has outsized leverage over fixing individual functions. Two passes of that shape — 609 orphan functions, then 512 data-referenced pointers — have each produced more movement than any single-function fix in this project's history.

Open defects

Nine, and four are happening every run

Written up individually so each can be picked up on its own. The red stripe marks wrong behaviour occurring in every single run right now; amber marks a flaw in the tooling that analyses the work rather than in the work itself.

R3 A two-instruction fragment is skipped, so a function returns without restoring its caller’s registers The correct repair is written out and deliberately withheld: applying it takes execution from 582 kernel calls to 48, because the broken version was returning early and skipping work that then runs and fails. Blocked on whatever that work hits.
R4 A second skipped fragment, with no repair path at all Recompiling it was tried and measured worse: the tool sizes a function by scanning forward to a return instruction, and here that ran 693 bytes through several unrelated functions when the real one is 41. Its true owner is still unknown.
R5 A newly exposed fragment — an array fill, a hundred-iteration loop, and a register restore Absent from the previous census because the paths that reach it had not opened yet. Exactly the shape of the defect fixed earlier today, which moved three counters at once. The most promising item on this list.
R6 A fourth skipped fragment the recompiler refuses to handle It reports no terminating instruction, so the existing tool has no answer. Needs either a better size-finder or a hand-determined range.
R1 The signal the project calls most meaningful is neither recorded nor checked Its own definitions file names “code reached” first, as the only measure with real resolution. The progress log has no field for it, and the stall detector never tests it. It appears in 39 of 193 entries, in prose.
R2 The progress tool advertises a best figure that was a runaway Described above. Every session is told it stands far below a record that never existed.
R8 Restoring hand-written repairs duplicates three functions, every time Deterministic, reproduced three times, and one copy is a hybrid carrying a label belonging to a neighbouring function. A new tool now repairs it by checking that every label inside a function belongs to that function’s own address range — but the duplication itself is unfixed.
R9 The integrity check reports “could be placed” as though it meant “is present” The direct cause of four repairs being lost and a whole baseline being measured wrong earlier today. The presence test this audit used belongs in the tool.
R7 One unexplained drop in 193 recorded runs 2 August, kernel calls 92 to 72, no note. Every other large movement in the history carries an explanation. Low priority; it is the only gap in an otherwise complete record.
