Root cause: one uninitialised object

Inside that initialiser, a type descriptor reaches the create-an-instance path with both its instance size and its allocation prefix set to -1. The code allocates size + prefix, so it asks the heap for 0xFFFFFFFE bytes — roughly 4 GB. The allocator correctly refuses and returns null, and the pointer becomes 0 + (-1) = -1, which passes a non-null check and is written through.

Probing all 235 allocator calls made this unambiguous: the healthy ones request 12, 16, 52 bytes; the fatal one requests 0xFFFFFFFE. Nothing in the chain is misbehaving — not the allocator, not the null check, not the create path. One object was never initialised.

The fix belongs at the top of that chain. Every function below it is faithful to the original and none of them should be guarded. It is also the third time the same defect class — code reachable only through a data pointer, so never translated — has produced the active wall.

The dominant defect class

Code that exists but is never reached

A recompiler discovers functions by following calls from an entry point. A function whose only reference is a pointer in a table — a vtable, an initialiser list, a factory array — is never reached, never translated, and whatever it was meant to set up stays null for the whole run.

The clearest case sits on the most important path in the binary: the CRT startup at 0x001A1C23 is never the target of a call instruction anywhere. Its only reference is push 0x1a1c23, as an argument to CreateThread. It runs at all only because it was hand-written into the port.

The strategic read

Anything that converts data-referenced code into translated code has outsized leverage over fixing individual functions. Two passes of that shape — 609 orphan functions, then 512 data-referenced pointers — have each produced more movement than any single-function fix in this project's history.

What happens next

One named target unlocks the rest

The sequence below is not a wish list. Each step is blocked only by the one above it, and the first has already been named by the project's own callee-save checker.

1 — sub_0021E970 — done, and it was not what the plan predicted

The plan said its epilogue was misaligned. It is not. The address it exits through, 0x0021EABF, is a real two-instruction fragment — set a register, jump back into the middle of the same function — that the translator never recognised as code. So the exit called a placeholder whose entire body discards a return address, and the function returned with its epilogue never run: five saved registers abandoned on the stack, and the caller handed back a loop counter where it expected an object pointer. That counter, 23, is the value an earlier investigation chased for weeks. The fragment is now inlined where it belongs.

This one is proved from the original machine code rather than from a run, because the function is not reached on the current boot. The census it prompted is where the measurable gain came from.

2 — re-apply the field-container fix

A single edit, already written and verified to work: create the field container at registration when a descriptor has none. It was reverted only because the wall above sits in front of it.

3 — retire the guards

Ten of this session's changes are diagnostic bypasses, and each says so in its own comment. With registration writing into real containers they should become inert. Every one gets removed and re-measured on its own.

What the census changed

The same defect class looked enormous statically and turned out to have five live members. Two of them are now real functions rather than placeholders, which is the whole of this session's measured gain. One must never be recompiled the way the tool proposed: it derives a function's size by scanning forward to a return instruction, and here that ran 693 bytes through several unrelated functions when the real one is 41. The other two are a matched pair, and they need the fragment inlined rather than recompiled — a mid-function continuation carries the epilogue's pops without the prologue's pushes, so it is only correct while the frame it belongs to is still alive.

The lesson generalises past this project: measure a defect class before sizing it. The gap between 2,061 and 5 is the difference between a rewrite and an afternoon.

Two other threads stay open. A scanner written earlier found 379 indirect calls that mix register saves with argument pushes; none can be corrected mechanically, and each is a latent version of the defect that cost wall 42. And one wall is deliberately left unguarded, because it sits inside the allocator's own free list, where a wrong skip corrupts the heap silently instead of crashing.

The honest caveat

Part of the depth reported above rests on those bypasses rather than on correct behaviour. Applying the real fix will make the numbers look worse before they look better, and that is the right trade: a bypass that becomes load-bearing has stopped being a bypass.

That stopped being hypothetical this session. The correct fix for one of the two paired fragments is faithful to the original machine code, and applying it takes execution from 582 kernel calls down to 48 — because the broken placeholder had been returning early and skipping work that now runs and fails. It lands the boot directly on an older wall the plan already names. The fix is reverted and recorded word for word, to be re-applied once that wall is cleared. Reverting a correct change is the right call here; pretending the number it produced was a regression would not be.
