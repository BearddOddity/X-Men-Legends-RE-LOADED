Where it stands right now

A predicate that always said yes, and a baseline that was measuring a damaged tree

The translator emits the two-instruction idiom for “was this zero?” but never the flag that carries the answer between them, so 269 comparisons across the binary evaluated as a compile-time constant. One of them asks whether an allocator owns a pointer, and it was answering yes for every pointer. Fixing it does not unblock what the plan said it would - and checking that turned up something worse: the previous run’s figures were taken from a tree that had silently lost four hand-written fixes. Root cause: one uninitialised object

Inside that initialiser, a type descriptor reaches the create-an-instance path with both its instance size and its allocation prefix set to -1. The code allocates size + prefix, so it asks the heap for 0xFFFFFFFE bytes — roughly 4 GB. The allocator correctly refuses and returns null, and the pointer becomes 0 + (-1) = -1, which passes a non-null check and is written through.

Probing all 235 allocator calls made this unambiguous: the healthy ones request 12, 16, 52 bytes; the fatal one requests 0xFFFFFFFE. Nothing in the chain is misbehaving — not the allocator, not the null check, not the create path. One object was never initialised.

The fix belongs at the top of that chain. Every function below it is faithful to the original and none of them should be guarded. It is also the third time the same defect class — code reachable only through a data pointer, so never translated — has produced the active wall.

The dominant defect class

Code that exists but is never reached

A recompiler discovers functions by following calls from an entry point. A function whose only reference is a pointer in a table — a vtable, an initialiser list, a factory array — is never reached, never translated, and whatever it was meant to set up stays null for the whole run.

The clearest case sits on the most important path in the binary: the CRT startup at 0x001A1C23 is never the target of a call instruction anywhere. Its only reference is push 0x1a1c23, as an argument to CreateThread. It runs at all only because it was hand-written into the port.

The strategic read

Anything that converts data-referenced code into translated code has outsized leverage over fixing individual functions. Two passes of that shape — 609 orphan functions, then 512 data-referenced pointers — have each produced more movement than any single-function fix in this project's history.

What happens next

A correction first, then the next thread

The previous entry reported 582 kernel calls and 501 call sites. That measurement was taken from a damaged tree: regenerating one generated file discards the hand-written fixes inside it, and the tool that checks for those fixes answers “all 1,095 can be placed” whether or not they are actually there. Four were missing, including one that makes an allocator ownership test honest. With them restored the same build measures 230 and 477. The lower number is the real one.

What was actually fixed

neg r; sbb r, r; inc r is how a compiler of that era asks “was this value zero?”. The middle instruction reads a carry flag the first one sets. The translator emits both instructions and never the flag, so the whole idiom folds to a constant — the answer is always “yes, equal”. It appears 404 times; at 269 of them the two instructions sit adjacent in one basic block, where the flag is knowable with certainty, and those are now correct.

The remaining 135 take their carry from a comparison further back or from another path into the same code. Those are left alone. Guessing a plausible value there would be manufacturing data to get past a check, which is the one thing this project does not do.

A pleasing confirmation: months ago this same defect was found by hand at exactly one of those sites and fixed the same way. The new tool skips that site, because it was already right.

It did not, however, unblock the change it was supposed to. That change still collapses the boot, so the dependency the plan described was wrong: the fixed function was blocking a different repair, not this one.

The next thread, and it is a sharp one

The defect this project has been chasing for weeks — type descriptors whose field container is missing — is gone. All fourteen now have real containers and real arrays, and the fix written for it is measurably a no-op, so it was deleted rather than kept as dead code.

What replaced it is more specific. Six of the fourteen have a field pointer aimed at another object’s array, while their own sits unused at a fixed offset the other eight use correctly. That is not a null pointer or uninitialised memory; it is one object holding a reference to another’s data. Aliasing like that has a single cause, and finding it should collapse several walls at once.

The honest caveat

Two of today’s corrections cost more than they gained on the headline counter, and both were kept anyway. A predicate that answers truthfully sends execution down paths that a predicate stuck on “yes” never reached, and those paths fail. Indirect dispatches rose 21% while kernel calls fell — more real work happening, over a shorter run. The counter that dropped is the narrower measure.

One thing was lost for good. The regenerated file cannot be rebuilt to match what it replaced, and no archive had been taken since early August. The project has a tool for exactly this and it was not used.
